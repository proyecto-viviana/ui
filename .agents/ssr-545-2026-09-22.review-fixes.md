### Measured, not asserted

The commit's note called the double build "unmeasured". It is measured now. A
throwaway jsdom probe (`packages/viviana-ui/test/zz-probe-611.test.tsx`, written,
run, and deleted in this session — it asserts the *fixed* count, so committing it
would have locked a red test into the suite) rendered each field with
`prefix={<Probe/>}` and counted calls to `Probe`:

```
NumberField instantiations: 2   NumberField probe nodes: 1
ColorField  instantiations: 2   ColorField  probe nodes: 1
ComboBox    instantiations: 2   ComboBox    probe nodes: 1
Tests  3 failed (3)   — each `expected 2 to be 1`
```

One whole component built and discarded per render, on every one of them. An
adornment with an `onMount`, a ref or a context registration fires twice and the
discarded copy never unmounts.

### Why it does not throw, and what stays unmeasured

Class 2 crashed because `TextField` handed `PrefixInputProvider` a *computed* id
set (`prefixId={adornmentIds()}`), and that thunk re-read the adornment from
inside the input's ref callback, which Solid 2 applies with `getOwner() ===
null`. None of the seven does that: each passes `prefixId={prefixId}`, a plain
`createUniqueId()` string, and `withPrefixLabelledBy`'s thunk
(`packages/viviana-ui/src/field/prefix.tsx`) resolves `() => props.prefixId` —
the prop, never the adornment. So the ownerless read path is absent, which is
what the commit's note claimed and what the source shows.

Unmeasured, and said so in the ticket: whether the discarded build is symmetric
across server and client under hydration. Nothing but a client probe was run.

### Disposition

Not fixed here. #545's Scope writes "the published package source a named route
proves wrong", and no route proves these — `vp run test:routes` reaches 173/175
with them in place. Seven sites across two published packages, six components,
a changeset and a per-component proof is its own ticket, and during the
soft-launch cut it is not a change to make on the side of a review pass. Opened
as **#611**, with the seven paths, the measurement, the fix shape copied from
`textfield/index.tsx`, and the guard idea the reviewer suggested as its optional
second half.

## 2. The count doubt in the note was false

The note ends "Note the count too: `Done when` says 174 routes, the spec file
reports 175 tests." There is no discrepancy.
`apps/web/e2e/route-sweep.spec.ts:31` declares one guard test — "the route list
is derived from the generated tree and is not empty" — and `:43-46` declares
exactly one test per `ALL_ROUTES` entry. `ALL_ROUTES` is `parseRoutes()` from
`apps/web/src/app/seo/route-manifest.ts`. Run on this tree:

```
$ vp exec tsx -e "…parseRoutes()…"        # in apps/web
ALL_ROUTES.length = 174
MINIMUM_EXPECTED_ROUTES = 169
EXIT=0
```

175 = 1 + 174. `Done when`'s 174 routes is exactly right, and the writer's own
173 passed / 2 failed of 175 is consistent with it. Left standing, the doubt
invites the next agent to "reconcile" 174 → 175 and make the criterion
unsatisfiable.

**Taken differently from the reviewer's instruction, on purpose.** The reviewer
asked for the sentence to be replaced in the note. This board does not edit
history entries: the third note on this very ticket retracts a wrong entry in a
later one "rather than edited, because the mistake is worth keeping". So the
resolution is appended as the next entry and names the sentence it answers.
