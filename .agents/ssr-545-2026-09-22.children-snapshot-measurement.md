# #545 — do the four baselined `children()` sites freeze after hydration?

2026-09-22, `ui` main, base `385929c4`. The previous slice closed
`guard:idiomatic-solid` by baselining four sites with the argument that the
`children()` memo keeps its reactivity. That argument had no runnable proof
behind it. This slice measures it, keeps the baseline, and writes the rule
where the guard's next reader will be. No published source changed.

## 1. The claim under test

`385929c4`'s ticket note justified the baseline rows with:

> the memo still tracks `local.prefix`, and anything reactive inside the
> adornment keeps its own reactivity, so the snapshot the rule warns about is
> not the defect here

That is a statement about what hydrated DOM does after a signal changes, and
nothing in the repository ran it. #135 is the ticket where this class cost us
real breakage, so the measurement copies its method: render on the server,
hydrate over that exact markup, flip a signal the adornment reads.

## 2. The experiment

Extended the twin class 2 already owns rather than adding a third copy:

- `packages/viviana-ui/test/fixtures/textfield-adornments.tsx` — new
  `TextFieldReactiveAdornmentsFixture` with `prefix={<Keyboard>wrapped:
  {count()}</Keyboard>}` (signal read wrapped in an element) and
  `suffix={<>bare: {count()}</>}` (bare mixed text, #135's exact shape), plus
  two field-free controls that differ only in where the snapshot is read:
  `SnapshotInJsx` reads `resolved()` inside the JSX expression,
  `SnapshotInBody` reads it once into a local in the component body.
- `packages/viviana-ui/test/TextField.ssr.test.tsx` — one case writing the
  three server documents into `output/`.
- `packages/viviana-ui/test/TextField.hydrate.test.tsx` — a `hydrateAndFlip`
  helper and three cases. The helper captures the host elements
  (`input, kbd` / `em[data-control]`) before hydration and asserts identity
  (`toBe`) after, so an "it updates" reading cannot be a subtree Solid threw
  away and rendered fresh.

Result on the shipped shape:

```
$ vp test run --config vitest.ssr.config.ts packages/viviana-ui/test/TextField.ssr.test.tsx
3 passed  EXIT=0
$ vp test run --config vitest.hydrate.config.ts packages/viviana-ui/test/TextField.hydrate.test.tsx
4 passed  EXIT=0
```

`wrapped: 0` / `bare: 0` before the flip, `wrapped: 1` / `bare: 1` after, in
the server's own nodes, no hydration mismatch. The in-JSX control goes
`control: 0` → `control: 1`; the in-body control stays `control: 0`.

## 3. Fails first, on the real component

A harness whose freezing case never freezes proves nothing, so the same claim
was run against a deliberately broken `TextField`. Temporarily read both
snapshots once in the component body
(`packages/viviana-ui/src/textfield/index.tsx`), regenerated the SSR half, ran
the hydrate half:

```
AssertionError: expected 'Ask the tutorwrapped: 1bare: 0' to contain 'bare: 1'
1 failed | 3 passed  EXIT=1
```

Reverted with `git checkout -- packages/viviana-ui/src/textfield/index.tsx`;
4 passed, EXIT=0.

Read which half failed. Frozen, `wrapped: 1` still updated: an element-valued
adornment carries its own insert effect inside itself, so it cannot freeze this
way. Only bare mixed text discriminates. An experiment run with a
component-valued adornment alone — the obvious fixture, since that is what
`/showcase/inputs` uses — would have reported "live" off a shape that has no
failure mode. That is why the fixture carries both.

## 4. Verdict

The four sites are false positives of a heuristic that cannot see, from the
AST, where the snapshot is read. They stay baselined with `ticket: 545`; no
component source changes. The rule that decides it is now in
`scripts/check-idiomatic-solid.ts`'s anti-pattern-2 rationale, with the twin
named and with the reason the heuristic stays broad: a site measured benign is
baselined with the ticket that measured it.

> Retracted 2026-09-22, same day, by section 6: at the time this was written
> only the two `textfield/index.tsx` rows were rendered. "The four sites" was
> two measured and two inspected. Section 6 measures the other two and the
> verdict then stands as written.

## 6. Review of `358e509c`, 2026-09-22, base `358e509c`

Two findings, both real, both in the evidence rather than in a component.

### 6.1 Half the SSR half could not fail

`expect(adornments).toMatch(/wrapped:[\s\S]*0/)` is vacuous: `[\s\S]*` spans
the rest of the document and a `0` always follows in a class atom, an id or a
hydration key. Measured on the committed server markup by substituting the
adornment's `0` with `999` and re-running each assertion:

```
site                 old /label:[\s\S]*0/     new /label: (?:<!--[^>]*-->)*0</
                     real   999               real   999
textField/wrapped    true   true              true   false
textField/bare       true   false             true   false
searchField/wrapped  true   true              true   false
searchField/bare     true   false             true   false
inJsx/control        true   false             true   false
inBody/control       true   false             true   false
```

Both `wrapped` assertions passed a server render of `999`. The four others
discriminated only because no `0` happened to follow them in that markup, which
the next class-name or hydration-key change would have taken away. Replaced by
a `serves(label, value)` helper that matches across the hydration markers and
stops at the tag closing the text node; the table above is its acceptance test.
The hydrate half's `before` assertions were the only honest half and are
unchanged.

### 6.2 "The four sites are measured" was two measured, two inspected

Section 2 rendered `TextField` only. The `searchfield/index.tsx:426` and `:427`
rows rested on source inspection, and SearchField's render is not TextField's:
it gates the prefix through a `<Show>` with a fallback (`:579`), the input
through a second keyed on either adornment (`:590`), the suffix through a third
(`:597`), inside a div carrying its own `isFocusWithin` signal. A `<Show>` that
re-rendered there could re-resolve a snapshot where TextField's would not.

Measured now, not inspected. `SearchFieldReactiveAdornmentsFixture` carries the
same two adornment shapes; the SSR case writes
`output/viviana-ui-searchfield-reactive-adornments-ssr.html` and the hydrate
case flips the signal over it, asserting node identity first, like its twin.
Result: `wrapped: 0` / `bare: 0` before, `wrapped: 1` / `bare: 1` after, in the
server's own nodes, no mismatch.

Fails first, on the real component. Same narrow mutation section 3 used, this
time in `packages/viviana-ui/src/searchfield/index.tsx` — render a body-read
snapshot at `<FieldPrefix>`/`<FieldSuffix>`, leaving the memos live for the
`<Show>` conditions and `adornmentIds` — then regenerate the SSR half and run
the hydrate half:

```
AssertionError: expected 'Find a tutorwrapped: 1bare: 0' to contain 'bare: 1'
1 failed | 4 passed  EXIT=1
```

Only the SearchField case failed; the TextField case stayed green, so the new
case is what guards the new rows. Reverted with `git checkout --`; 5 passed,
EXIT=0.

### 6.3 Measured while there, not claimed: how much has to freeze

Section 3 reports `wrapped: 1` surviving the freeze. That holds for the narrow
mutation only. Resolving the `children()` memo itself once in the body —
`const prefixFrozen = children(() => local.prefix)()`, every downstream read a
constant — freezes both halves in both components:

```
TextField    AssertionError: expected 'Ask the tutorwrapped: 0bare: 0' to contain 'wrapped: 1'
SearchField  AssertionError: expected 'Find a tutorwrapped: 0bare: 0' to contain 'wrapped: 1'
```

So section 3's "only bare mixed text discriminates" is true of where the
*rendered* snapshot is read, not of where the memo is resolved. Both forms were
run here; the fixture carries both adornment shapes for the narrow one, which is
the weaker signal and therefore the one worth guarding.
