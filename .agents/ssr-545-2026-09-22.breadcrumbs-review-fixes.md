The claim: `vp run guard:idiomatic-solid` exits 1 on four `children()`

Confirmed, measured here rather than quoted. With the baseline as `748070a1`
committed it (`git show HEAD:scripts/idiomatic-solid-children-baseline.json`

```

  packages/viviana-ui/src/searchfield/index.tsx:426 prefixNode — add to the baseline with a ticket id
  packages/viviana-ui/src/searchfield/index.tsx:427 suffixNode — add to the baseline with a ticket id
  packages/viviana-ui/src/textfield/index.tsx:325 prefixNode — add to the baseline with a ticket id
```

EXIT=1. `.github/workflows/certification-gates.yml:194` runs it, so this is a
blocking gate and not a local nicety.

Baseline entry, not a source change, and the reason is in the guard's own
message and in the shape of the rule. The heuristic flags a `children()` whose
result is read as content; here that is the whole point of `096776df` — a
JSX-valued `prefix`/`suffix` is a getter that rebuilds the component on every
read, and the input's ownerless ref callback re-read it and threw. `children()`
resolves it once under the field's owner. The memo still tracks `local.prefix`,
and anything reactive inside the adornment keeps its own reactivity, so the
snapshot the rule warns about is not the defect here.

Applied: the four rows, `"ticket": 545`, written by the generator rather than by
hand — `vp exec tsx scripts/check-idiomatic-solid.ts --write-baseline`, EXIT=0,
33 sites. That also refreshed `generated` from `2026-09-02` to `2026-09-22` and
the informational `line` numbers of the 29 pre-existing rows, which had drifted
since September 2.

One step past the finding: `ticketForChildrenSite` had no `/textfield/` or
`/searchfield/` case, so regenerating the baseline would have relabelled the
four new rows `#192` — the file would have stopped reproducing itself the first
time anyone ran `--write-baseline`. It now returns 545 for those paths, and the
doc comment says why the ticket there is the reasoning and not a debt.

Proof that fails first, in `scripts/check-idiomatic-solid.test.ts`: two new

Verified while here, because it decides whether the four rows are half a pair:
`packages/solid-spectrum/src/searchfield/index.tsx` has no `local.prefix` or

## 3. The breadcrumbs comment read as a parity claim over a divergence

The claim: "Upstream S2 renders `HiddenBreadcrumbs` unconditionally and measures
in a layout effect (@react-spectrum/s2 Breadcrumbs.tsx:527, :542): first render
never reads the environment either way" is true fact by fact but reads as "we
match upstream here", when upstream emits the hidden copy on both sides of the
first render and we now emit it on neither.

Confirmed. Every cited fact re-read in the pinned `@react-spectrum/s2` 1.7.0
source under `apps/comparison/node_modules`: `src/Breadcrumbs.tsx:542` renders
`<HiddenBreadcrumbs …/>` unconditionally, `:527` is the `useLayoutEffect` that
measures, and `:452` seeds `useState(collection.size)` — fully expanded — where
ours seeds `MAX_VISIBLE_ITEMS - 2`. Both are divergences, and parity is this
repository's first rule, so a comment that hides them is how they get "restored"
and hydration breaks again.

The comment in both `packages/{viviana-ui,solid-spectrum}/src/breadcrumbs/index.tsx`
now says so plainly, keeps the version and line citations, names the second
divergence the reviewer spotted, and ends "Do not \"restore\" either to
upstream's shape." Comment only; the two files stay a baselined diverged pair
and `guard:layer-boundary` is green.
