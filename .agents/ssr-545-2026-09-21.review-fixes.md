# #545 — review of `d3ccc7cc`, three findings, all real

2026-09-21, `ui` main, base `d3ccc7cc`. A reviewer raised three problems against
the landed module-scope-JSX work. Each was measured against the tree before
anything was changed. All three held. One of the two fixes the reviewer proposed
for the second was measured wrong and taken the other way round.

## 1. A concise-body IIFE walked straight past the guard

`findModuleScopeJsx` descended into an immediately-invoked function with
`ts.forEachChild(node.body, visit)`, which visits a body's *children* and never
the body node itself. A block body has children; a concise arrow body **is** the
expression. So:

```tsx
export const icon = (() => <svg width="16" viewBox="0 0 16 16" />)();
```

evaluated JSX at module evaluation and the guard exited 0 on it. Measured with
`findModuleScopeJsx` over seven forms:

| form | before |
| --- | --- |
| `(() => <svg …/>)()` | `[]` — missed |
| `(() => { const n = <svg />; return n; })()` | flagged |
| `(function () { return <svg />; })()` | flagged |

Fixed by `ts.isBlock(node.body) ? ts.forEachChild(node.body, visit) : visit(node.body)`.

## 2. A callback a module-scope call runs before it returns

Any function boundary read as call time, so all four of these built JSX at
module evaluation — reproducing this ticket's defect exactly — and the guard
reported nothing:

```tsx
const icons = NAMES.map((n) => <Icon name={n} />);
const three = Array.from({ length: 3 }, () => <Icon />);
["a", "b"].forEach((n) => { registry[n] = <Icon />; });
const sun = untrack(() => <Sun />);
```

The reviewer proposed visiting *every* callback argument of a module-scope call,
with "a small allowlist of deferring callees if needed". The tree says the
opposite. An ancestor-based sweep of the seven published `packages/*/src` roots,
1750 files, visiting every callback argument:

- **55** module-scope callback-argument sites,
- **3** JSX hits, and all three are call time, not module evaluation:
  - `packages/solid-spectrum/src/skeleton/index.tsx:256` — `createLeafComponent`
  - `packages/viviana-ui/src/skeleton/index.tsx:285` — `createLeafComponent`
  - `packages/solidaria-components/src/TokenField.tsx:186` — `createHideableComponent` → `createMemo`

Most module-scope callbacks in these packages are component factories: a callee
here takes a callback in order to *defer* it. So the rule is an allowlist of
eagerly-invoking callees, `EAGER_CALLBACK_CALLEES` — the array iterators plus
`Array.from` and `untrack` — not a denylist of deferring ones. With it,
`vp run guard:idiomatic-solid` is EXIT=0 on this tree: 0 false positives, and
the four shapes above are caught.

The remaining blind spot — a callback run at module evaluation by a callee
outside the list, `runNow(() => <Icon />)` — is now named in the doc comment on
`findModuleScopeJsx` and in the ticket's Scope, which used to claim the guard
"refuses module-scope JSX in every published package". It never did.

## 3. Half the shipped claim had no proof

The changeset, the source comment and the guard's own failure message all say:
"In the browser the same binding is one DOM node shared by every trigger on the
page, so a second trigger takes the first one's icon." Every test that landed
runs under `vitest.ssr.config.ts`, where a module-scope icon compiles to an
`ssr()` string that can be emitted any number of times. The SSR case
`gives each instance its own icon markup` asserts `html.match(/<svg/g).length`
is 2, which a shared string satisfies; it failed pre-fix only because the warm
render earlier in the same file had already poisoned the module. The SSR half
was proved; the browser half was not tested at all.

Added, both packages, under the DOM config:

- `packages/solid-spectrum/test/ContextualHelpTrigger.test.tsx` — two cases
- `packages/viviana-ui/test/ContextualHelpTrigger.test.tsx` — NEW file, two cases

Each renders two triggers and asserts two distinct `<svg>` nodes. Against the
pre-fix component source (`d3ccc7cc^`), both packages:

```
× gives each trigger on a page its own icon node        (solid-spectrum)
× gives each info-variant trigger its own icon node     (solid-spectrum)
× gives each trigger on a page its own icon node        (viviana-ui)
× gives each info-variant trigger its own icon node     (viviana-ui)
  AssertionError: expected …(1) to have a length of 2 but got 1   ×4
Tests  4 failed | 16 passed (20)          EXIT=1
```

`length 2 but got 1` **is** the shared node: inserting one element in two places
moves it, so the second trigger takes the first one's icon and the first goes
blank. On this commit, 20 passed, EXIT=0.

The SSR case is renamed `renders an icon for every instance` and carries a
comment saying what it can and cannot see, with a pointer to the DOM test.
