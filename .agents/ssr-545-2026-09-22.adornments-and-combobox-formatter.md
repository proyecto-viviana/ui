# #545 — classes 2 and 3, the two routes this seat was given

2026-09-22, `ui` main, base `4ac92800`. Two of the five routes left red by the
module-scope-JSX commit: `/showcase/inputs` (class 2, a client throw inside a
JSX-valued `suffix`) and `/solid-spectrum/docs/components/combobox` (class 3, a
hydration mismatch after the description slot). Each cause was reproduced in a
test before anything was changed.

## 1. A JSX prop is a getter, and one of its readers has no owner

`suffix={<Keyboard>↵</Keyboard>}` compiles to `get suffix() { return
createComponent(Keyboard, …) }`, and `createComponent` is `untrack(() =>
Comp(props))` — not a cached node. Every read runs the component body again.

`TextField` read `local.prefix`/`local.suffix` five times: twice per `<Show>`
(the `when` and the body) and once more inside `adornmentIds()`, the thunk
`PrefixInputProvider` hands to the headless field for the input's
`aria-labelledby`. That last read is the one that kills the page: the headless
`Input` read `context.inputProps` **inside its ref callback**, and Solid 2
applies element refs through `runWithOwner(null, …)` (`@solidjs/web`'s `ref(fn,
element)`). `withPrefixLabelledBy`'s `inputProps` trap calls the thunk eagerly,
so the adornment's body re-ran with `getOwner() === null`, and anything it
reaches that needs an owner throws — for `Keyboard`, the hydration key.

Fix, in three files:

- `packages/viviana-ui/src/textfield/index.tsx` and
  `packages/viviana-ui/src/searchfield/index.tsx` resolve each adornment once
  with Solid's `children()` — already imported in this chain, no new dependency
  — and every later read is of the resolved node.
- `packages/solidaria-components/src/TextField.tsx` reads
  `context?.inputProps?.ref` in the component body, where an owner exists,
  instead of inside the ref callback, in both `Input` and `TextArea`.

Upstream gets this free: a React element is an inert object, so re-reading the
prop runs nothing. Nothing about the rendered output changes — the regression
case asserts both adornment ids still join the input's accessible name.

The jsdom client test alone does **not** throw: by the time `adornmentIds()`
reads the getter, the earlier `<Show>` read has already built a node under a
live owner, so the ownerless read gets an `HTMLSpanElement` back and only the
instance count (8 where 1 is right) shows the defect. The throw needs the
hydrate environment, where the re-run has to claim a hydration key. That is why
the pair is a counting test plus an SSR/hydrate twin, and why this was invisible
to every existing suite.

## 2. A client-only reactive node shifts every hydration key after it

`createComboBox` built its announcement string formatter behind a guard:

```ts
const stringFormatter = !isServer ? createStringFormatter(comboBoxIntlStrings) : null;
```

`createStringFormatter` allocates reactive nodes (`createStringDictionary` plus
a `createMemo`), and Solid 2 hydration keys are a per-owner path — so the client
allocated ids the server never did and every sibling key after the combobox's
hook shifted by the same amount. Most claims degrade quietly when a key misses;
help text does not. `description`/`errorMessage` render through `Text` →
`ElementTag` → `dynamic`, whose claim has no fallback, so the shift surfaced as
`Hydration Mismatch. Unable to find DOM nodes for hydration key` and the route
error boundary ate the page.

Upstream has no such guard. Pinned `react-aria@3.52.0`,
`dist/private/combobox/useComboBox.mjs:75`, calls
`useLocalizedStringFormatter(intlMessages, '@react-aria/combobox')`
unconditionally at the top of the hook body; `grep -n "isSSR\|typeof window"`
over that file is empty. Fixed by doing the same, which also retires the
`!stringFormatter` half of three effect guards (the `isServer` half stays: those
effects announce to a live region).

One fix covers both registers: `solid-spectrum` and `viviana-ui` both compose
`@proyecto-viviana/solidaria-components`' headless `ComboBox`, which is the only
caller of `createComboBox`. Neither styled copy changed, so the layer-boundary
baseline is untouched. `grep -rn "!isServer ?"` over `packages/*/src` now
returns one line, `createInteractionModality.ts:427`, which picks a *value* per
side and creates its signal on both — not this shape.

## Left standing, on purpose

Seven `<Show when={local.prefix}>…{local.prefix}</Show>` sites still read a
JSX-valued adornment twice and so build it twice — `solid-spectrum`
`numberfield/index.tsx:508`, `textfield/index.tsx:422`, `combobox/index.tsx:1051`,
`color/index.tsx:1379`, and `viviana-ui` `numberfield/index.tsx:510`,
`combobox/index.tsx:1066`, `color/index.tsx:1377`. None of them hands the prop
to a thunk that an ownerless ref re-reads (each passes a plain `prefixId`
string), so none throws and no route proves them wrong. Wasteful, not broken,
and unmeasured — recorded here rather than fixed blind.

`ElementTag`'s fallback-less claim is what turned a shifted key into a thrown
page. Giving it a fallback would have hidden this defect instead of surfacing
it; leaving it is the better behaviour, and the diagnosis file
(`plan/ssr-545-cd-diagnosis.md`) keeps that reasoning.
