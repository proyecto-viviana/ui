## 1 (high) — the FIXTURE branch was a bypass with one signal

`GITHUB_API_URL` on a loopback host was accepted on that alone. Pre-fix, with a
loopback server answering one invented success row per required workflow:
EXIT=0, `PASS: all required workflows succeeded for exact release SHA`, the
word FIXTURE in the line its only defence.

Fixed: a loopback base also needs `RELEASE_EVIDENCE_FIXTURE=1`. Either signal
alone refuses. Post-fix on the same server with the variable cleared: EXIT=1,
`no RELEASE_EVIDENCE_FIXTURE=1 beside it`. The docblock sentence "There is no
bypass and no 'if disabled, skip' branch" is retracted in place and replaced by
the name of the one pair that is an exception.

## 2 (high) — `RELEASE_SHA` disarmed the refusals no API read can replace

Naming HEAD's own forty digits on this dirty tree: pre-fix EXIT=0 PASS. So the
previous note's "an explicit `RELEASE_SHA` is untouched, because that is CI's
path" published a working tree, one variable away from the local route the same
commit had just closed.

Fixed: `resolveSha()` reports `fromHead` and `isHead`. The clean-tree refusal
runs whenever the judged revision is HEAD, however it was named — post-fix
EXIT=1, `the working tree is not clean`. Naming another revision (HEAD~1) on
the same dirty tree still passes: that asks about that revision.

Decision this seat made, recorded because the review did not make it: the
`origin/main` containment refusal stays on the from-HEAD route only. A CI
checkout has no `refs/remotes/origin/main` to compare against, and the API read
already proves the sha ran as a push or dispatch on this repository's own main.
A dirty tree is the part no API read can see, so that one runs on both routes.

## 3 (high) — the verdict was order-blind

A red run followed by a green re-run at the same sha refused forever: pre-fix
EXIT=1, post-fix EXIT=0.

Fixed: runs at a sha sort newest-first on `run_started_at`, then `run_number`,
then id. The newest completed run that is not `cancelled` or `skipped` decides.
A cancellation stands aside without hiding the red beneath it; a sha whose runs
are all cancelled is still no evidence; and a refusal on a newest red says when
an older green stands behind it.

## 4 (medium) — the local publish route uploaded without reading drift

`changeset:publish` at HEAD was prerequisites, evidence, build, publish, while
`release.yml` ran `guard:publish-drift` before the same upload. This reverses
the decision recorded on #599 that drift "is release.yml's and widening the
local route is not this ticket": both routes push the same tarballs.

## 5 (high) — the drift guard deadlocked the release it guards

Measured against a loopback registry serving what npm served on 2026-09-21
(0.5.1, 0.4.3, 0.5.1, 0.6.4, 0.6.3): `node scripts/check-publish-drift.mjs`
EXIT=1, all five packages named, each `a pending changeset is queued on top of
that bump`. That step runs before the changesets action, which is both stages —
so the version stage, the one move that consumes the changeset and supersedes
the bump, was blocked by the guard standing in front of it.

Fixed: `--version-stage` defers an unpublished bump a pending changeset covers,
and nothing else. `release.yml` passes it; `changeset:publish` runs the guard
plain, where nothing is left to defer to. Same fixture registry post-fix: plain
EXIT=1 as before, `--version-stage` EXIT=0 with five deferral notes. The
`unpublished-bump` message now names the recovery it always owed.
